# 后续闭环评测默认策略

用户于2026-10-14要求后续评测复用本次线程控制策略，并考虑更多CPU线程。此偏好用于后续明确授权的新评测，不自动新增当前评测回合，不修改正在运行的worker。更多线程与更多worker是两个独立参数。

- 每个RTX5090 worker默认申请1GPU、14CPU、60GiB，Spot调度，最多96GPU小时。遵守当前共享规则与其他作业归属，不占用未授权标准卡。
- 新worker启动时，默认候选设置为PyTorch intra-op 4线程、inter-op 1线程，OMP/MKL/NUMEXPR 4，OpenBLAS 1，OMP_WAIT_POLICY=PASSIVE、GOMP_SPINCOUNT=0、KMP_BLOCKTIME=0；必须在评测器导入及计算前生效，保存实际线程数证据。此设置已有罐藏食物实测，不能宣称已验证全部100任务或所有机器。
- 更多线程的候选为6、8；不能直接把全部线程池设为14或宣称线程越多越快。下一轮在正式回合开始前，用独立且不计分的固定预热/性能片段比较4、6、8线程，记录实际CPU配额、持续仿真步速、CPU节流、视频开销和稳定性，选择实测更快的配置，再冻结整批配置。不同实例的成绩不能作为选择线程配置的依据；不得为测速重跑已经完成的正式回合，也不得在成绩间挑分。若扩大CPU申请规格，另行核验资源规则与实际配额，不自动增加本任务CPU/GPU申请。
- 每worker默认连续执行5个不同实例回合，复用模型与可复用的仿真进程。对长耗时任务可减少为1–2个回合以缩短尾部；全部固定实例仅执行一次，不改变官方超时、模型权重、任务选择或原评分规则。
- 允许扩大运行中的worker数量；保留最多10个待调度GPU worker，UNKNOWN、排队、启动中均计入，RUNNING不计入10。无需网页闲时容量作为提交前提；提交者唯一、保存准确名称/UID，未知结果先核对，不重复提交。
- 每轮查询、验收、补交结束后等待约45秒。按有限计划持续补交，已有运行worker增长不要求同步提高pending上限。
- 下一轮运行前将通用线程设置接入实际新启动链路，验证所有任务范围的启动兼容，并记录各类任务的实际步速。当前campaign的CPU4专用代码仅放行canning_food实例303–305，不得直接移作全任务通用launcher，也不得绕过该范围断言。
- 当前实测证据：eval_results/sco_submission1000_1688977_20261013/diagnostics/canning_cpu_affinity/failure_g001/ETA_CURRENT.json，约45秒窗口内罐藏食物303–305为7.76–8.42步/秒；此前不同实例/时间窗口1.1–1.5步/秒，仅作参考，不是全任务固定加速倍数。
- 保留每回合同次原始JSON、完整MP4、配置、源码/权重身份与恢复链。完整结果只做CPU产物修复，不重跑挑分。新启动的随机种子及进程内随机状态重置策略需事先固定并披露，不能声称不同批分组的随机轨迹相同。
- 禁用曾复现崩溃的进程内异步faulthandler诊断；使用外部只读进度/OS计数器。不要复用已回滚且降低步速的8核在线affinity限制。

1000回合按每worker 5回合约需200个有限worker作业。实际完成时间由初始化、任务长度、录像、尾部与验收共同决定，不按GPU数量无限线性缩短。
